# LiveSuite 低延迟视频协议

这是 LiveSuite 私有的通用视频传输协议。协议实现归根应用所有，位于 `native/livesuite-quic/`；它不属于、也不依赖 `stream-server/`。安卓端通过统一推流抽象选择 RTMP、QUIC 或 UDP，摄像头页只是本协议的真机测试入口，录屏入口使用同一个协议实现。

## 传输选择

- QUIC：默认端口为 UDP/1935。控制、时钟同步和统计走双向可靠流；全部视频帧走持续的可靠单向流，音频走独立的可靠单向流。
- UDP：默认回退端口为 UDP/9444。复用完全相同的媒体分片格式；配置帧和关键帧重复发送一次。
- HTTP-FLV：默认端口为 TCP/8080。带 `.flv` 后缀的地址返回原始 HTTP-FLV，供 OBS、VLC、ffplay 等常见软件拉取；不带后缀的同一路径返回内置浏览器播放器，不经过临时文件。
- 各端口都可在 LiveSuite 页面调整。若 Windows 防火墙只放行 UDP/1935，可把需要测试的传输放到 1935，另一个媒体端口换开。

局域网内优先尝试 QUIC；在已知链路、追求更低尾延迟时可选择 UDP。UDP 不提供拥塞控制或可靠关键流，因此依赖 FEC、关键帧重复和短队列保持可恢复性。

## 媒体帧

每个媒体包使用 60 字节大端序头，魔数为 `LSQ1`，协议版本为 3。头部包含：

- 包类型、帧标志和头长度；
- 64 位会话号与 32 位帧序号；
- 采集、编码完成的墙钟时间，以及编码器 PTS；
- 完整帧大小、分片序号/总数；
- FEC 组起点/大小、分片大小和有效负载大小。

视频数据为 H.264 AVCC。音频通过可靠媒体流传输；推流握手会附带实际 `AudioRecord` 单组采集时长，HTTP-FLV 输出据此补偿音频同步水位。默认推流只进入 HTTP 输出，不创建媒体文件。

## 拉流、录制与回放缓存

- 外部软件使用 `http://<LiveSuite IP>:8080/<推流路径>.flv` 拉取。例如 `/phone/stream` 对应 `http://192.168.137.1:8080/phone/stream.flv`。OBS 中可添加“媒体源”、关闭“本地文件”后填入该 URL。
- 浏览器直接打开不带 `.flv` 的地址，例如 `http://192.168.137.1:8080/phone/stream`，会加载内置自同步播放器。页面只显示当前视频流；播放器使用浏览器 WebCodecs 解码 H.264（低延迟模式），并在收到实际 AAC 配置时按媒体时间戳同步解码音频。`latent=毫秒数` 仅由网页读取，用于额外延后当前播放器的每帧显示，以补偿该路流本身的产出延迟；`audiolatent=毫秒数` 只把声音再向后移。LiveSuite 关闭 `include-audio-in-pull` 或推流本身没有音频时，不会创建音频解码器；断线、时间线倒退或解码器丢步后会自动重连并等待关键帧。若浏览器阻止自动播放音频，点击画面一次即可解锁。
- 播放器的音频经 AudioWorklet FIFO 连续输出，PCM 域 WSOLA 控速只改变节奏、不改变音高，1x 时按位透传。同步组公共控速限制在 ±0.5%，本地声卡漂移校正限制在 ±0.5%，合计不超过 ±1%；本地误差先滤波，6ms 死区内回到透传，速率变化按真实经过时间限速，FIFO 储备不足时不会为追赶而加速。解码、裁剪和 FIFO 入队共用同一音频时间映射，包含画面实际呈现滞后与 `audiolatent`。每块音频使用对应提交记录的 FLV 时间戳，源空洞补静音，严重迟到的孤立块丢弃，未来的有效压缩块保留；静音边界做短淡入淡出。正常缓冲微调保持 PCM 连续；只有公共时钟确认严重欠载并重新蓄水时，FIFO 才暂停消费并保留已排队的 PCM，等待帧不计入已播放的音频位置。
- Android 的一批 PCM 会拆成多个 AAC 包；浏览器在解码、WSOLA 和入队余量之外，按完整采集组、实测音频到达间隔及时间戳确认窗口的最大值预留缓冲，并上报到统一同步预算。PCM 拼接按采样数连续推进，可疑 FLV 时间戳跨采集组确认后才补洞或去重，最多暂存 8 块；小幅持续时钟偏差只调整媒体标记，由保音高闭环平滑吸收。断流时暂存有超时出口，不永久扣留最后的有效 PCM。`audioDiagnostics()` 增加 `timestampJitterBlocks` 和 `pendingPcmMs`；`npm run test:browser-audio-packetization` 覆盖批量采集时间戳抖动、真实 AAC 丢帧、重复包与采集时钟漂移。
- 临时大预算回落后，如果旧公共时钟落后当前目标超过 1 秒、整组都尚未呈现且每条必要音视频轨已就绪，持续确认后统一恢复起播。已经播放过的组只有在所有必要音视频轨至少 1 秒没有实际进度、旧位置已不在缓存内、各页面共同缓存覆盖当前目标附近位置时才允许恢复；缺反馈、缺轨道或仍在出声都会否决。`startupRecoveryRevision` 和 `stalledRecoveryRevision` 分别标识起播与停滞恢复，页面按版本只执行一次，并清除旧时钟下的延迟请求、观测窗口和在途音频解码；不能把向前恢复当作补静音。重连同样清除上一条源的浏览器预算。
- 视频队列容量、未来 GOP 判定和音频积压检查同时覆盖公共时钟的**实际延迟**。目标预算回落不代表已有延迟立即消失，不能用数百毫秒的新目标去裁剪仍按数十秒旧时钟等待的有效帧或反复清空 FIFO。
- 起播先等 FIFO 状态和声卡输出时钟实际前进，再选取第一段应当出声的媒体数据，避免设备启动时间变成音频积压。音画同步从出声时刻之前的 FIFO 历史状态外推，不把尚未听到的渲染量子当作已播放；历史最多保留 128 项。超过 400ms 的异常偏差需持续 300ms 才触发重新起播，单次时钟抖动不清空声音。
- 网络抖动由已有缓冲与公共控速吸收；一次停顿后集中到达的陈旧帧不构成持续加大预算的证据。源端真正缺帧时保留 PTS 空洞，不能回放旧帧或用额外缓冲伪装成完整源。音频源缺口以实际时长填补，并在 PCM 边界做 3ms 淡出/淡入；单个 AAC 块缺失不重启 FIFO。网络与源侧缺帧不用于下调本地显示容量，只有实测绘制耗时、rAF 达标率和长帧能证明本地性能不足。帧间隔统计会如实包含源缺帧造成的长间隔，稳定段和源端缺口应分开评估。
- **启用流同步时，时间对齐和缓冲水位由全部活跃播放器中最慢的音频或视频轨共同限制。** 服务端按固定时间间隔计算唯一公共速率，加速必须得到全部轨道水位的允许；所有页面从同一个服务端时钟锚点外推播放位置。视频解码或音频处理持续缺少余量时，各轨分别上报公共延迟。正常预算变化通过连续时钟和平滑控速吸收。重新蓄水要求同一轨的新反馈连续至少 500ms 缺数据且实际播放位置没有前进、该轨所需预算（或原生预算）比实际延迟多至少 100ms；不能用另一条健康轨的大预算放大一次空队列。上一轮等待期间不累计下一轮欠载，旧反馈重复读取也不能触发暂停。
- `sync-info` 与播放反馈返回相同的 `sharedPlaybackClock`（时钟标识、版本、服务端时间锚点、媒体位置锚点、速率和累计重新蓄水量 `rebufferedUs`）。漏收中间控速响应形成的小锚点差不能触发音频等待，等待仅执行明确的新增蓄水量。较晚到达的旧响应不能覆盖新时钟；反馈短暂超时会移除过期的水位与额外预算，但不会重置仍在播放的公共时间轴。`sourceAlignmentDelayMs` 是原生收流预算，`alignmentDelayMs` 包含浏览器处理预算；`audioDiagnostics()` 提供各轨所需预算、原始/滤波音画误差和公共时钟。同步模式只补回用户明确设置的页面 `latent`；关闭同步时保留独立播放器的本地自适应延迟。
- `sync-info.playbackDiagnostics` 提供实际/目标延迟、重新蓄水次数和最近触发记录，以及各页面构建版本、反馈新鲜度、各轨进度/欠载持续时间和共同缓存范围。`alignmentRequest` 保存浏览器提出请求时的缺口、实际延迟、时钟版本、音频到达/处理提前量和视频解码提前量；服务端只在真正重新蓄水时打印 `[LiveSuite] shared playback rebuffer`。执行 `npm run observe:quic-playback -- http://127.0.0.1:8080 60` 可只读采样 60 秒并保存 JSONL 到 `tmp-quic-playback-observation/`，旧版服务仍可观察时钟与预算跳变；新观测字段需运行更新后的服务并刷新播放页面。`npm run test:quic-playback-stall` 覆盖空队列误触发、跨轨预算串扰、旧反馈、实际缓冲容量和整组停滞恢复。
- AudioWorklet 不可用、模块加载失败、处理器出错或实际停止状态回报时，自动改用 ScriptProcessorNode 承载同一个 FIFO；`audioout=script` 可强制回退。正常重同步会重置本轮输出等待窗口，避免把旧首块的时间误当成超时。浏览器拒绝自动播放时显示“开启声音”按钮，任意页面交互也能解锁。有音频配置且上下文运行中却持续无输出时，控制台每 5 秒输出 `[LiveSuite] 音频持续无输出` 诊断。
- 服务端对齐延迟不使用设备相关的固定毫秒预留。每条流按音频轨、视频轨分别在“真实到达 cadence × P95 尾概率倒数”的时间窗内统计“服务端收到时刻 − 预测采集时刻”的 P50/P95；稳定预算只使用一次 P95，尾差最多贡献一个实测 cadence。拉流处理余量来自该轨实测到达间隔，音频再加发送端上报的实际 PCM 采集组时长。所有量都来自当前流的到达时间或媒体格式，所有流共享其中最大的已确认预算。延迟上调以真实经过时间确认，而不是按包数触发：观察时长取原始 P95 候选相对当前预算的差值；同一时刻批量到达的任意多个旧包或单个严重迟到包都不会拉长所有视频的时间轴。若断线重连后的帧持续到达、但还原出的采集时钟不前进，该轨会在一个实测统计窗口后结束校准并被判为陈旧积压，其迟到帧由播放器丢弃，不再拖慢正常流；同一路径用新 session ID 重连时会立即接管发布槽并关闭旧拉流缓冲。同步浏览器在每条已注册流的必要音视频轨完成首次窗口校准前不会起播；窗口一旦确认会立即抬高共享时间轴。内置播放器立即取得已经到达的帧，把“实测显示时刻 − 实际到达时刻”的全部剩余量用于解码、WSOLA 和 FIFO。共享延迟按剩余超额的 1%/秒平滑回落，较大错误预算能较快收回、接近目标时又不会抖动；关闭同步时同样按到达分布计算，但不低于用户配置值。`sync-info` 提供 `alignmentReady`、`pullLeadMs` 与每条流的 `videoLatencyP95Ms`、`audioLatencyP95Ms`、`videoArrivalCadenceP95Ms`、`audioArrivalCadenceP95Ms`、`audioGroupDurationMs`，播放器 `audioDiagnostics()` 会原样带出。
- 视频呈现按显示器刷新驱动调度，满刷新率时直接使用 rAF，避免第二层截止时间因亚毫秒误差误丢整个显示节拍；需要抽帧时才按绝对截止时间限频。展示帧率依据本地 rAF 达标率连续自适应，源侧可变帧率不会成为本地上限。当源帧间隔恰为整数个显示节拍时，呈现相位会居中，30fps@60Hz 同样生效；校正只作用于 canvas，限制在半个显示节拍内，不改变公共媒体时钟。相位尚未稳定时不把暂时漏呈现误判为设备性能下降。带 `debug=1` 打开页面后，可从播放会话读取 `lastMeasuredPresentationFps`、`lastPresentationIntervalStdDevMs` 与 `audioDiagnostics()`。`npm run test:browser-playback-quality` 覆盖实际播放器的 30/60fps 帧调度、带抖动的连续 PCM、音高、起播时钟及公共缓冲微调。
- HTTP-FLV 拉流由 Electron 主进程提供（`src/main/quicPull.ts`），各连接独立保存封装时间轴和待发队列，排队超限的连接会断开重连；启用同步时，播放时钟、速率与所需缓冲仍由整组音视频反馈共同决定。
- HTTP 输出内部只保留 codec 配置与当前 GOP，供新拉流端从关键帧快速起播；这部分始终存在，但不属于用户控制的回放缓存。起播快照保留音视频配置及按媒体时间排列的全部帧，不要求收包序号递增；新播放器接入不会推进已有播放器的取帧位置，避免丢失音频配置或接入期间的媒体帧。
- 录制按推流会话独立控制，多条流可同时录制，开始或结束任意一条都不会中断其他流。接收端不重新编码，直接将该流在录制期间的 H.264 封装为分片 `.mp4`。
- 回放缓存也按会话独立控制，每条流可设置 5–300 秒的缓存时长，并可在不中断缓存的情况下随时导出 MP4。缓存以关键帧为边界，最大占用为每路 256 MiB；断流后已形成的可解码缓存仍可保存，结束该路缓存会立即释放内存。
- 录制和回放文件均保存到系统“视频/LiveSuite/Recordings”目录。分片 MP4 在写入过程中也保持可读取，异常退出时比尾部才写索引的普通 MP4 更容易恢复。

## 延迟与质量策略

- 单个数据报以协商出的最大数据报为上限，默认约 1200 字节，避免 IP 分片。
- 每 8 个媒体分片生成 1 个 XOR 校验片，可重建每组中的任意 1 个缺失分片。
- 安卓发送队列最多保留 4 帧；拥塞时优先移除最旧的非关键帧，避免延迟无限累积。
- 编码器关闭 B 帧并请求 Android 低延迟模式；配置帧与关键帧获得额外保护。
- 接收端乱序等待默认 12 ms，不完整帧的最大生存期默认 150 ms。超过预算就丢弃，不用持续缓存换取完整性。
- “残余丢片”是 FEC 后仍无法恢复的分片比例；“FEC 重建”会包含因乱序而由校验片提前重建的分片，不能直接等同于网络丢包率。

## 延迟范围测量

客户端和服务端每 2 秒进行一次四时间戳同步：客户端发送 `t0`，服务端接收和回复时记录 `t1/t2`，客户端收到时记录 `t3`。由此得到服务端相对客户端时钟偏移的上下界：

```text
offset_min = min(t2 - t3, t1 - t0)
offset_max = max(t2 - t3, t1 - t0)
rtt = (t3 - t0) - (t2 - t1)
```

服务端收到帧时，用采集时间和偏移上下界计算端到端延迟区间；编码耗时由编码完成时间减采集时间得到。界面保留端到端延迟范围，但编码耗时改为最近 240 帧的平均值和 P95，避免把同一设备时钟上的编码抖动误写成测量范围。

## 2026-08-12 真机联测

设备 V2302A，经 `192.168.137.0/24` WLAN 推送 1920×1080、H.264 High、约 2.5 Mbps、30 fps：

| 传输 | 端到端范围 | 编码范围 | 接收帧率 | 结果 |
| --- | --- | --- | --- | --- |
| QUIC/1935 | 常态 72–145 ms；长跑窗口峰值 157 ms | 63–89 ms | 约 30 fps | 约 70 秒丢 1 帧，残余丢片 0% |
| UDP/1935 | 63–115 ms | 65–101 ms | 约 30 fps | 丢帧 0，残余丢片 0% |

早期联测的两份裸 H.264 都通过 ffmpeg 全量解码且无错误；现在裸流仅用于这次历史结果，不再作为 LiveSuite 的运行时输出。该设备声明支持 1080p/60 和 1080p/240，但实测 60 fps 只输出约 30 fps，240 fps 在 5 秒内没有编码输出；稳定配置应使用 1080p/30。当前局域网环境下 UDP 的尾延迟优于 QUIC，因此可将 UDP 作为超低延迟档，QUIC 作为需要可靠关键数据和拥塞控制的默认档。

## 2026-08-13 输出联测

设备 V2302A 使用 QUIC/1935 推送 `/phone/stream`，HTTP-FLV 被 ffprobe 识别为 H.264、1920×1080、约 30 fps，ffmpeg 连续拉取并完整解码无错误。默认模式没有生成媒体文件。运行中开启录制后生成的 MP4 被 ffprobe 识别为标准 `mov,mp4` 容器，H.264 全量解码通过，未出现 DTS 非单调告警。回放缓存也通过了“启动缓存 → 停止手机推流 → 推流结束后保存”的回归，导出的 7.5 秒 MP4 可完整解码。

双流回归使用两个独立会话同时推送。会话 A 单独开启录制、会话 B 单独开启 7 秒回放缓存时，另一会话的状态保持不变；随后两路可同时录制和缓存。停止 A 的录制与缓存后，B 仍继续运行。B 断流后其缓存条目保留，可单独导出 MP4；结束该缓存后条目和内存随即释放。三个联测 MP4 均具有完整的 `ftyp`/`moov` 初始化段和 5 个 `moof`/`mdat` 媒体分片。
